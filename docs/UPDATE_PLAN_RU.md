## 2. Решения и границы

1. **Исследования открыты.** Последнее указание владельца отменяет прежнее предположение о закрытости исследовательского снимка. Существующие исследования включены и сохраняются. Повторно собирать их для переноса не нужно. Учетные секреты остаются конфигурацией окружения. Экспорт пользовательских записей и изменение аудитории сайта — отдельные действия; открытость исследований не меняет их автоматически.
2. **GitHub — исходники, Sites — публикация.** Рабочая ветка `develop`, релизная `main`. Приложение не пишет в исследовательский репозиторий. Планируемый CI проверяет код, но не выполняет deploy/merge/review автоматически.
3. **Одна модель.** Для `ai-capex-signals` сохраняется Challenger 2.1 и действующая политика. Не создавать второй Challenger и не менять caps/веса/критерии квалификации средствами панели.
4. **Снимок — исторический источник.** В MVP обязателен ручной режим. Live read-only GitHub — отдельное расширение после проверки поддерживаемой интеграции, не условие завершения MVP.
5. **Разные измерения статуса.** Каноническая квалификация, ручное предложение, полнота, freshness, необходимость пересчёта, CI, человеческий review и merge хранятся раздельно.
6. **Без нового исследования по умолчанию.** Обновление интерфейса использует уже зарегистрированные события, артефакты и журналы. Новый ресерч возникает только по новому существенному факту или конкретной доказанной ошибке.

В этапе 0 эти противоречия устранены в ТЗ v1.2 RU/EN: код уже перенесён, исследования открыты, целевая приёмка ещё не завершена. Методология и расчётные правила не менялись. Доказательства исходной точки — [IMPLEMENTATION_BASELINE.md](IMPLEMENTATION_BASELINE.md), статусы A01–A18 — [ACCEPTANCE_TRACKER.md](ACCEPTANCE_TRACKER.md).

### Этап 2 — согласованные снимки, provenance и надежный импорт

Приоритет P0. После этапа 1. Предлагаемый PR: `feat: add versioned research snapshot imports`.

- Ввести пакет снимка: repository, branch/ref, commit SHA, cutoff, observed_at, schema/model/policy versions, hash и отдельный origin для main/PR/manual. Для разных источников сохранять собственные metadata, не присваивать всем один main SHA.
- Пакет включает существующие registry, daily index, reports, coverage/weekly manifest, calculation artifacts, open checks, strength/macro и GitHub snapshots. Поддержать прежние отдельные registry/calculation JSON.
- Хранить принятые снимки неизменяемо; активный срез — ссылка на snapshot ID. Рабочие заметки и решения сохраняются отдельно от источника. При необходимости вынести тела снимков из общего payload в отдельную D1-таблицу, чтобы каждое ручное сохранение не пересылало все исследования.
- Перед принятием показать предварительную сводку: новые/неизменённые записи, добавленные reviews, конфликты, отсутствующие блоки и происхождение. Частичный импорт явно PARTIAL; отсутствующий блок не означает удаление старого доказательства.
- Проверять на сервере те же правила, что и на клиенте: ID/key/hash, неизменяемость факта, review-prefix, URL/даты, модели/политики, размер в байтах, дубликаты ID/key и causal_root_id + effect_id. Подозрительные экономические совпадения направлять на ручную сверку, не объединять автоматически.
- Повторный идентичный импорт — no-op. Новые reviews дописываются; конфликт не заменяет прежнюю запись. Ошибка импорта оставляет активный срез и ручные заметки нетронутыми.
- Экспорт содержит достаточно данных/метаданных для восстановления workspace без зависимости от текущего `seed.json`. Сохранить CSV только для видимых строк и защиту формул.

Проверка: два одинаковых импорта дают ноль новых событий; исправленный ключ/переписанный старый review/другая модель отклоняются; два различных эффекта одного корня не считаются независимыми без проверки; прямой POST не обходит валидатор. Export → import восстанавливает тот же контекст.

Готово, когда все экраны получают согласованный набор данных и A02/A04/A14 подтверждены. Исходный snapshot остается доступным; неизвестные значения и metadata не выдумываются.

### Этап 3 — события, календарь и очередь пересчёта Challenger

Приоритет P0. После этапа 2. Предлагаемый PR: `feat: complete event review and Challenger artifact workflow`.

- Карточка события: первичные источники и их класс, публикация/known-public-by/факт/регистрация, точность, исходное/финальное решение, маршрут, counterevidence и отдельная ручная история.
- Поддержать неизвестную фактическую дату без падения фильтра, сортировки и календаря. План `CAL-...` хранится отдельно и не увеличивает число EVT; после появления источника связывается с существующим/импортированным событием.
- На сервере сохранять reviewer, rationale и дату решения; переход в QUALIFIED, снятие квалификации, исправление signed effect/PIT/дубликата направляют решение в REQUIRED. NOT_REQUIRED требует причины. Ручное решение остается MANUAL, а не канонической квалификацией.
- Очередь пересчёта связывает событие/причину/cutoff/PR с конкретным новым артефактом. Импорт результата не снимает все REQUIRED автоматически: соответствие cutoff, версии и исправлению подтверждается отдельно.
- Общая выборка для обзора и истории: отдельно последний канонический результат и последний доступный manual/proposed срез. Для каждой строки — собственные R2/R3/R5/R6/R7, источники, interval/exact/null, coverage, included/excluded IDs, review_by и artifact SHA.
- Не менять калькулятор. Partial артефакты разбирать по контракту исследования: допустимые неизвестные компоненты показывать UNKNOWN; структурно некорректный файл отклонять, а не заполнять его прошлыми значениями. График — отдельные интервалы без интерполяции и midpoint.

Проверка: QUALIFIED → withdrawal и исправление PIT требуют решения о пересчёте; отсутствие нового JSON не создаёт чисел; истёкший review_by не удаляет историческое QUALIFIED; новый отчёт не наследует результат. Проверить явно неизвестные даты и смену часовых поясов.

Готово, когда A03/A05/A09/A10 подтверждены, календарь не смешивает планы и факты, ручные решения сохраняют историю.

### Этап 4 — отчёты, полнота и продолжение проверок

Приоритет P1. После этапа 3. Предлагаемый PR: `feat: complete reports coverage and resumable checks`.

- Ежедневные и еженедельные отчёты получают период/NY-session, cutoff, связанные ID, расчётный артефакт, источник, PR и заметки. File presence, source completeness и manual workflow status независимы.

- COMPLETE проверять на сервере по всем десяти уникальным checkpoints; ручной итог не меняет PARTIAL исходного манифеста. Смена связанного head SHA делает attestations CI/review неактуальными для текущей ревизии, сохраняя старые отметки в истории.
- Полнота: фактический статус выбранного weekly manifest, блоки/пробелы/freshness, сверка ожидаемых и найденных ID; показывать отсутствующие/лишние/повторные ID, а не только совпавшие количества.

- Обзор «подтверждено / не завершено / следующие действия» строить по этим записям; убрать выводы и активные задачи, навсегда зашитые под 10–11 ноября. Исторический контекст сохранить, не удалять.

Проверка: повторный период не клонируется; девять checkpoints не дают COMPLETE; совпадение counts при другом составе ID показывает расхождение; сохранённая проверка восстанавливается и продолжается без нового исследования. Due-date сама не открывает завершённый аудит заново.

Готово, когда A06/A07/A08 подтверждены, а обзор и манифест относятся к выбранному срезу.

### Этап 5 — GitHub-трекинг, сила доказательств и макро

Приоритет P1. После этапа 4. Предлагаемый PR: `feat: add SHA-aware GitHub tracking and macro provenance`.

- PR: URL/number, state/draft, head SHA и observed_at. CI: inspected SHA, conclusion, URL/time. Review: reviewer, decision, reviewed SHA, unresolved threads. Merge: merge SHA, время и источник подтверждения. Неизвестное — UNKNOWN.
- Ручной ввод поддерживает все эти поля, не только общий overlay. Изменение SHA сохраняет историю и помечает старые CI/PASS как относящиеся к прежней ревизии. Успех CI не означает human PASS; отсутствие review не означает одобрение.
- Восстановить точную provenance strength/macro из данных: origin, PR/main, ref, source SHA, method/policy version, cutoff. Proposed материал всегда имеет метку и ссылку на соответствующий PR.
- Макро: отдельные сопоставимые серии/периоды, actual/prior/consensus-vintage при наличии, источники, канал, overlap group и ограничения. Совместный эффект — anchors/подтверждения/противоречия/неизвестные/триггер, сценарии base/downside/upside.
- Не суммировать ordinal ranks и не создавать signed delta из MACRO_ONLY. Нет данных о magnitude — качественный UNKNOWN.

Проверка: head SHA изменился — прежний green CI/PASS не показывается текущим; unmerged макро не появляется как main; нет review — не PASS; макроранги не складываются с корпоративными. Любое сетевое взаимодействие приложения с GitHub остается read-only; при MVP достаточно ручного режима.

Готово, когда A11/A12/A15 подтверждены.

Проверка: RU/EN + фильтр + открытая карточка + возврат; CSV содержит ровно видимые записи; пустой/частичный снимок не ломает экран; ошибка загрузки не показывает «Сохранено». Проверить телефон 390 px и desktop, а также форму с длинным русским текстом.

Готово, когда A01/A13/A17 и интерфейсная часть A16 подтверждены.

### Этап 7 — сквозная приёмка и подготовка релиза в Sites

Приоритет P0 для релиза. После этапов 0–6. Предлагаемый PR: `test: verify acceptance and prepare Sites release`.

- Добавить CI именно в WTF-Viewer: установка по lockfile, контрактные проверки, TypeScript, production build и необходимые интеграционные тесты. Проверки не привязывать навсегда к 38 событиям/PR #196; исторический fixture проверять отдельно от общего алгоритма.
- Сквозной сценарий: импорт снимка → событие → ручное решение → REQUIRED → отдельный артефакт → отчёт/десять checkpoints → ручной текущий-SHA CI/PASS/merge evidence → продолжение проверки → export/restore.
- Проверить две вкладки с одинаковой revision, отказ Origin/identity, серверный обход клиентских проверок, ошибку БД/сети, recovery draft и отсутствие ложного success.
- Проверить миграцию на копии прежних данных, backup/restore, отсутствие потери reviews/заметок и сохранность canonical IDs. Данные текущего исследования повторно не регистрировать.
- Обновить реестр A01–A18: фактический PASS/FAIL/BLOCKED, команда/сценарий, среда, SHA и evidence. Непроверенный hosted сценарий не считать PASS по локальной сборке.
- Подготовить точный commit/build для публикации существующего Site с сохранением project_id, D1 binding и аудитории. Перед применением миграции — проверенный backup. При откате учесть данные и schema compatibility: старый bundle сам по себе не восстанавливает БД.
- Слияние в main и публикация являются отдельными действиями по указанию владельца; этот план их не выполняет. После разрешённого deploy проверить вход, сохранение, reload, конфликт вкладок и версию снимка на самом hosted Site.

Готово, когда все обязательные A01–A18 имеют подтверждённый результат; нерешённые блокеры явно перечислены. Для релиза hosted persistence и миграция не могут оставаться «предположительно работают».

### Отдельный последующий этап — read-only GitHub Refresh

Вне обязательного MVP, согласно §12 ТЗ. Начинается отдельной задачей после рабочего ручного режима.

Проверить доступность поддерживаемого runtime connector для GitHub, права и сценарий авторизации посетителя. Если поддержка есть — явный Refresh, независимо обновляемые источники, observed_at/SHA, stale/error и сохранение предыдущего снимка при отказе. Если поддержки нет — оставить работоспособный ручной импорт; не выдавать его за live. Запись, dispatch CI, reviews и merge из приложения не добавляются. Существующие AI CapEx Watch / Daily Close / Event Alerts не меняются.

## 5. Как вести выполнение

Рекомендуемый порядок PR: этапы 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Каждый — отдельная проверяемая поставка в `develop`; не создавать их заранее автоматически. Связи данных проектируются на этапе 1, а не заново для каждого экрана. Следующий этап не закрывается за счёт переноса нерешённого требования в бесконечную проверку.

На каждый этап сохранять: статус, полученный результат, текущий commit, пройденные проверки, незавершённое и следующую конкретную операцию. Блокер должен указывать недостающий факт/доступ/решение и условие возобновления. Срок или повторная дата сами по себе не запускают повторное исследование.

Не ставить сроки в днях до этапа 0 и пробной миграции: объём legacy-данных и hosted-проверок пока не измерен. Приоритет и зависимости выше определяют порядок, не обещание календарной даты.

## English summary

This plan upgrades the imported WTF Viewer prototype against the original specification v1.1, aligned in v1.2 during completed stage 0, and acceptance criteria A01–A18. Each stage includes concrete checks and an exit condition. Existing research IDs, reviews, artifacts and unresolved context must survive. No duplicate research, copied historical scores, changed model coefficients or repository mutations from the app are introduced. Live read-only GitHub Refresh remains a separate extension after the manual MVP.
